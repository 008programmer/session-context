Context Window
& Tokens
Context Window The maximum tokens Claude can hold at once. Claude Sonnet 4.6 supports 1 million tokens — roughly 750,000 words.
Token A chunk of text (~¾ of a word). Everything Claude reads or writes is measured in tokens — prompts, code, tool results, memory files.
Why It Matters Think of it like a whiteboard in a meeting — every tool call, memory file, and skill takes up space.

Why Context Engineering Matters
Better Output Quality
When Claude knows your project's stack and conventions — e.g. that you're on .NET 10 with specific library versions — it writes accurate, idiomatic code the first time, not on the third try.
Fewer Hallucinations
Pointing Claude at your real APIs, files, and patterns keeps it from inventing functions — e.g. it uses your actual UserService.GetById() instead of making up a plausible-sounding FetchUserById() that doesn't exist.
Reusable Instructions
Write your rules once in CLAUDE.md, skills, or memory — e.g. "always ask before creating a new Blazor component" — and every session, every teammate's Claude follows them automatically.
Clearer AI Reasoning
With your conventions spelled out — e.g. "reuse existing library components, don't write custom code" — Claude makes the same call you would, no back-and-forth.
Understanding
claude.md
What A markdown file Claude loads automatically every session
Why Without it, Claude starts blank — so either you re-explain it every time, or Claude searches and rediscovers it every time. Both burn tokens.
When Day 1 of any project; update as architecture evolves
Central instruction file — the AI's operating manual for your project, loaded automatically on every session
Architecture + coding standards — defines patterns, folder structure, tech stack constraints
Project constraints + workflows — what Claude should and shouldn't do in this codebase
No copy/paste required — rules are persistent, not re-typed into every chat
Risk — keep it current: every code change is the author's chance to update CLAUDE.md. If they skip it, the next teammate's Claude walks in the wrong direction and burns tokens re-verifying the real code.

Parallel vs Sequential
Parallel Multiple subagents spawned in one message — each runs simultaneously in its own context window
Sequential Second subagent waits for first to finish — use when output of one is input to the next
Conflict Two agents editing the same file in parallel will overwrite each other — always check file overlap first
Worktrees fix this: each agent edits in its own checkout — write conflicts become normal git merges, not silent overwrites
✅ Safe — different files
Agent 1 → Counter.razor, Counter.razor.js
Agent 2 → Weather.razor, Weather.razor.js
No overlap → run in parallel ✓
❌ Conflict — same file
Agent 1 → Counter.razor (alert button)
Agent 2 → Counter.razor (localStorage)
Write conflict → agent 2 overwrites agent 1 ✗
Fix A: merge into one agent
Agent 1 → Counter.razor (alert + localStorage)
Agent 2 → Weather.razor (CSV download)
Safe parallel again ✓
Fix B: git worktrees
Agent 1 → wt-A/ Counter.razor (alert)
Agent 2 → wt-B/ Counter.razor (localStorage)
Each agent → own checkout → merge later ✓
Memory & MCP
What Memory — notes Claude writes about you and your project. MCP — a way for Claude to talk to your other tools
Why Without Memory, every new chat forgets you. Without MCP, Claude only sees what you paste into the chat
When Memory works on its own — Claude saves stuff as you go. MCP turns on when you want Claude to reach into GitHub, the browser, a database, etc.
Model Context Protocol — how Claude reaches into your tools
Playwright CLI
vs MCP
Playwright CLI Agent runs shell commands — concise text output, skills loaded on demand. Best for coding agents working in large codebases
MCP Server LLM calls structured tools — full schemas + DOM snapshots stay resident in context. Best for specialized agentic loops
Trade-off CLI is cheaper on tokens; MCP is richer per call. Pick CLI for build-then-verify, MCP for exploratory automation

Context Discipline
Token Budget
  • Check /context often — know what's loaded.
  • /rewind to step back to a clean checkpoint — works best in single-scope chats; flaky when multiple scopes are in flight.
  • /clear between unrelated tasks — fresh context beats a polluted one.
  • /compact deliberately, not as a fix-all.
  • Use subagents to keep noisy work out of main context.
  • Prefer file paths and line numbers over pasting code.
  • Limit photo / screenshot size — every pixel becomes tokens.
  • Stale CLAUDE.md forces Claude to re-read the codebase to verify state — costly. Update it with your change.
  • Batch multi-step asks — chain #add #delete in one prompt instead of one task per round-trip.
Foundation & Planning
CLAUDE.md + Plans & Todos
  • Bootstrap CLAUDE.md with /init — short, explicit, brevity is performance.
  • Document layout, security, testing minimums; migrate toward AGENTS.md — reference, don't duplicate.
  • Use Plan Mode for any non-trivial change; Todos for multi-step work — mark done as you go.
  • Confirm approach before editing shared files.
  • Stale CLAUDE.md forces Claude to re-read the codebase to verify state — costly. Update it with your change.
Recipes + Workers
Skills & Subagents
  • Start with a skill — any agent can load it. One narrow job per skill, precise trigger.
  • Promote to a subagent only when the task needs its own model (e.g. haiku for cheap verification, opus for hard reasoning), its own effort/thinking budget, or a clean isolated context.
  • Parallel subagents when independent; sequential when one feeds the next.
  • Subagents can spawn subagents — a worker can call up a reviewer or escalate without bouncing back to main.
  • Never delegate understanding — you synthesize.
Force Multiplier
Superpower Skills
  • Just use them.
  • Heads up — they ask a lot of questions. Better plans come out the other side.
  • Hand the work to a subagent when it fits.
  • They teach you TDD as you go.
Make them yours. Don't treat superpowers as read-only — edit the trigger, drop bullets you ignore, add the constraints you keep repeating. This helps you understand them more.
Verification & Reversibility
Trust, Verify & Commit
  • For UI changes, open the app and click around. The diff can lie; the browser doesn't.
  • Let a separate, read-only helper check the work — it can't fudge its own homework.
  • In decision-making chats — when Claude is choosing an approach, library, or pattern — ask "where did you get that?". If it says "no" or "can't be done", don't take it at face value — ask it to point to the official docs.
  • Check it's reusing existing code, not rewriting helpers that already exist.
  • Check it's using libraries already in the project before pulling in a new one — or worse, hand-rolling its own.
  • For DB migrations, run dotnet ef migrations add yourself. Don't let Claude hand-write migration files.
  • Commit often. Small, working pieces. That's your undo button.
Experimenting
Command-line First
  • Don't launch from the VS GUI — use dotnet run or dotnet watch so Claude can see, suggest, and verify.
  • Same rule beyond .NET: git over the SCM panel, npm run over task runners, gh pr create over the web UI.
  • If your workflow lives in the terminal, Claude can pair with you. If it lives behind buttons, Claude is locked out.
  • Exception: drop into the VS debugger when you actually need breakpoints — best tool for the job wins.
